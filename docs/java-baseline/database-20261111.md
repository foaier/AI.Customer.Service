执行前备份并核对已部署结构和迁移记录，在维护窗口停止相关业务写入；同一数据库不能并发执行脚本。空库安装、本批既有版本的开发库和中断后的续跑均可从头到尾执行整份文件。已有表跳过，已知增量字段、索引和约束按当前数据库/schema 与所属表检查后补建；不删除表或业务记录，不回填会话，不重置在线代次和申请状态。`-- 合并来源文件：...` 与结束标记仍供定位和测试提取。

重跑保护面向本批脚本产生的已知结构，不是通用结构修复器：同名字段类型、索引列顺序或约束定义与预期不同时，需先核对差异，脚本不会自动改写未知版本。已有表缺少历史基础字段也不会因 `IF NOT EXISTS` 自动补齐。DDL 的其他错误必须停止处理，不能设置忽略错误后继续。

MySQL 执行器须支持末段 `DELIMITER $$` / `DELIMITER ;` 及 `PREPARE`，不能简单按分号拆分整文件。存在性判断使用当前 `DATABASE()` 的 `information_schema`；DDL 自动提交，失败后不能假定整体已回滚。CHECK 和触发器按最终状态范围重建，避免重跑时较早的调查来源约束拒绝已有 `SYSTEM_POLICY` 记录。保留 5.7 触发器及 8.x CHECK 分支；基线原声明 8.0.16+，历史 5.7 开发库记录不等于整份约束已完成目标版本验收。Kingbase 须正确处理 `$$` 函数体、`$cs_migration$` 匿名块、触发器和 COMMENT ON，存在性检查只查当前 schema，按部署事务策略提交。

结构保护保持字段业务含义、唯一性、复合隔离和最终状态机不变。原段中的“一次性/禁止重跑”、旧owner、旧功能开关和阶段边界说明保留为历史上下文，执行方式以本文件和合并文件头为准，现行数据owner与注册规则以[配置契约](configuration.md)为准。实时连接直接复用登录JWT。

当日后续三项简化没有新增表或字段：手动接单只要求登录、组权限及容量，原段中“ONLINE接新单”为历史规则；运行行仍用于容量串行锁与在线展示，首次操作由应用幂等初始化默认离线行。已部署库无需为这些简化重跑本文件。

2026-11-11 排查配置接口时，只读确认当前开发库缺少 `cs_reception_configuration`、`cs_reception_group`、`cs_reception_member`、`cs_reception_route` 和 `cs_handoff_route`。`SELECT version ...` 本身合法，驱动返回的实际原因为缺表（MySQL 1146 / SQLState 42S02）。切换 ORM 不会自动创建结构，需按上文前提执行对应方言整份合并文件补齐；本次没有对共享开发库执行 DDL。新版客服 HTTP 入口对驱动明确的缺表/缺列状态返回 `503 SCHEMA_NOT_READY`，提示执行当前迭代脚本，服务端保留根因；语法错误和连接失败不能冒充缺少迁移。

客服及关联 Conversation 持久化统一使用项目的 MyBatis-Plus / MyBatis-Plus-Join。普通插入、联表权限、指标聚合和分页均由 ORM 生成 SQL；并发初始化采用 ORM 插入与事务保存点，不再保留 MySQL/Kingbase 业务 SQL 分支。详见[持久化约定](persistence.md)。

新增两表均由客服owner唯一写入，按tenant/org隔离，不逻辑删除或级联删除。组织日历每组织一行，记录策略版本和更新主体；留言完整复合外键引用原waiting周期，正文只向原访客和认领者开放，邮箱仍保留在等待owner。MySQL5.7通过INSERT/UPDATE触发器限制版本和认领字段一致性，Kingbase使用同义CHECK。归档须与原工单和审计事实共同处理，不单独删除幂等键。

回滚前停止相关写入并导出审计及待投递事实，由数据 owner 按依赖逆序决定结构处置；本文件不提供自动删表或删除业务记录的回滚。归档沿用 tenant/org 隔离和各 owner 的生命周期，不增加级联删除。

本轮完整需求验收已在维护窗口保存开发库路由结构快照，补齐此前缺失的五张路由表与两张新增表；未删除或覆盖已有业务行。具体真实与隔离验证结果见[验收报告](requirements-e2e-20261111.md)。下文“未操作共享库”和28表数量仅描述各历史批次，不代表当前状态。
